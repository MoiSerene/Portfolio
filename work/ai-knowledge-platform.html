Case Study No. 03

Agent Creator Agent

Designed the conversational flow for Agent Creator Agent, which walks novice builders from a vague idea to a working AI agent without requiring prompt-engineering knowledge.

Role

Product Designer

Product

Trimble Agent Studio

Phase

Pilot

Users

Designers & small business owners

Business Goal

The minimum unit of customer value isn't creating an agent — it's creating and using a worthwhile agent in under 2.5 minutes. That splits into two design goals that don't automatically agree with each other: help people create an agent efficiently, and help them create one that's actually useful.

Most of what's interesting in this feature came from designing for both at once.

Users

Existing SketchUp, Trimble Connect, and ProjectSight users — for this phase, mainly designers/architects and small business owners, not dedicated PMs or IT staff. Nobody in this group has a developer on call.

Problem

A small architecture studio, or a solo/small-team designer running their own practice, already reaches for ChatGPT or Claude for the odd task — drafting a client email, summarizing notes.

What they don't have is a dedicated agent: something wired into their actual SketchUp models, Trimble Connect files, or ProjectSight data, built to run one specific job on repeat.

General chat memory is genuinely good now — it remembers your preferences — but it doesn't give you a connected, task-specific agent. Building that yourself, even with something like a custom GPT, means writing instructions and wiring up knowledge and actions by hand. For someone running a two-person studio, that configuration step is the wall.

The Tension

The fastest possible flow is a single text box — describe the task, get an agent, done in ten seconds. That satisfies “efficient” and quietly fails “useful,” because one sentence usually isn't enough to draft something differentiated for a specific SketchUp or ProjectSight workflow.

So the real design question was: which parts of the 2.5-minute budget buy usefulness, and which parts are just friction to cut?

What Shaped the Solution

Templates anchor expectations

People do worse starting from a blank box than from a template, even when they have a clear idea — a starting point tells them what “good” looks like.

Visibility builds trust

People trust an agent more when they watch it get built than when it's handed to them finished.

Control is not one-size-fits-all

A smaller, more technical-leaning segment wanted the opposite of guidance; for them, being asked questions is friction, not help.

The finding that mattered most for “useful”: left alone, people described their task but not their data — nobody volunteered “and here's my actual project file” or “connect this to my ProjectSight account” unless asked.

An agent built from a description alone ends up generic, doing basically what ChatGPT already does for them. The gap wasn't missing project context — it was that people didn't think to offer it. That's what made the nudge to attach knowledge a deliberate step, not an optional add-on.

The Solution, Mapped to the Two Goals

Efficient

Guided + form-based creation

Agent-guided creation as the default, with templates offered as optional starting points rather than required steps — that's where “reduce setup friction” actually happens for someone who's never built anything like this. Form-based creation exists as a second, faster lane for the more hands-on segment who wants to skip the conversation and just fill in fields — and the two aren't siloed; a user can switch between them mid-flow without losing progress, since they're really two views onto the same underlying agent.

Useful

Knowledge + visibility

The guided flow doesn't stop at a text description — it nudges the user to attach real knowledge (their actual project files, model data) or tools before the agent's first run, since an agent with nothing connected to it can't do much for a real SketchUp or ProjectSight workflow. Trust is built through visibility, not just live preview: as the agent builds, it's writing directly into the same form that powers the form-based path, so a user can switch over at any point and see exactly what the agent filled in — with a dot marking each field the agent touched, so nothing changes without the user being able to see it happened.

How This Gets Measured

Metrics are set on both sides deliberately, so one goal can't quietly win at the other's expense:

Efficient

Onboarding completion rate ≥50%, first-agent creation time under 2.5 minutes.

Useful

D7 return-to-agent rate ≥50%, and 80% of new agents having at least one knowledge source or tool attached before first run.

Not all of that is coverable with numbers, though. Completion rate tells you people finished, not that it felt easy; D7 return rate tells you who came back, not why the rest didn't. I'd close that gap with something light: a one-question prompt after first run (“was this easy to set up?” / “is this useful to you?”), plus a few interviews with people who finished onboarding but never came back — that second group is where the return-rate number stops explaining itself.

Where It Stands

Agent Studio is in pilot with a small set of Trimble customers, so there's no real usage data yet — I'll come back and fill this in once numbers exist.

What's Next

Once there's real usage data, the next step is going further than role-level: personalizing based on what someone's actually built and used, not just their job title, and adjusting elicitation depth to match.
